<objective>
**As a** developer letting the QA agent drive a real browser against my app, **I want to** be asked before it clicks anything that reads like "Eliminar", "Dar de baja" or "Confirmar pago", **so that** an autonomous UI run can never quietly destroy real data in my dev or staging environment.

Purpose: Phase 1 landed the API confirmation gate *before* the client could send anything more dangerous than a GET, on the explicit reasoning that retrofitting a guardrail after the agent already has broad access is materially riskier. This plan applies the same ordering to the browser: the UI gate lands in wave 2, before plan 02-04 teaches the orchestrator to click things. At no point in this phase does a browser-clicking capability exist without its gate already in place.

Output: the mechanical keyword classifier for element text and aria-labels, a `PreToolUse` hook retargeted from Phase 1's Bash-command parsing to Playwright MCP's tool-name and structured-argument shape, the judgment rubric that sits between them, and the orchestrator protocol in `SKILL.md`.

Implements D-05 (the confirmation-gate philosophy extends to the browser, pausing before a destructive-looking click exactly as the API gate does before a mutating method) and D-06 (detection by visible text and aria-label, since a button click has no HTTP verb to inspect).
</objective>
