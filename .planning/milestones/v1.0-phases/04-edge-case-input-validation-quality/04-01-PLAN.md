<objective>
Prove the phase's whole pipeline on one real discovered bound, end to end: the SQL
parser reports a machine-readable `{min, max}` for the fixture's
`CHECK (dia_cierre BETWEEN 0 AND 6)`, the generation protocol turns that into exactly
four boundary cases (min-1, min, max, max+1), those four cases live in a conforming
test-cases document with human-readable subcategory titles, and the document still
validates back through `test-case-doc.mjs`.

Purpose: DISC-04's systematic boundary coverage stands or falls on one question — can
a discovered constraint reach a generated case deterministically, without the
orchestrator re-reading SQL by eye? This plan answers it on the thinnest possible path
before the other five plans expand outward from it.

Output: `parseCheckBounds()` exported from `scripts/discover-schema.mjs`, a `bounds`
field on every constraint record `discoverSchema()` returns, the boundary rule in
`SKILL.md`'s `## Case generation protocol`, the subcategory-titling convention in
`references/test-case-format.md`, and an end-to-end test lock in
`scripts/discovery.e2e.test.mjs`.

systematically cover input-validation boundaries and negative/permission edge
scenarios, grounded in the constraints discovered in Phase 3, not just the happy path.

  <action>
Add an exported pure function `parseCheckBounds(checkExpr)` to `scripts/discover-schema.mjs`,
placed beside the other pure helpers and carrying the same "why, not just what" doc-comment
discipline the file already uses for `extractConstraints` — name the ambiguity it resolves
(an exclusive comparison is not the same bound as an inclusive one, and an unrecognised
expression is a different fact from no constraint at all).

Recognised shapes, in this precedence order: a two-sided `BETWEEN <a> AND <b>` first, then
the comparison operators `>=`, `<=`, `>`, `<`. `>=` and `<=` yield their literal operand.
A bare `>` yields operand plus 1 and a bare `<` yields operand minus 1, so an exclusive bound
is always reported as the adjacent inclusive value that the four-case rule can use directly —
guard the `>`/`<` patterns so they never match the `>=`/`<=` forms. Accept optionally-signed
integers and decimals. Return `{ min, max }` with either side `null` when only one side
resolved, and return `null` when neither side resolved. Never widen this to a general SQL
expression evaluator: anything outside these four shapes returns `null`, which is D-10's
discipline applied inside the parser, not just at the "no CHECK found" level.

Keep the regexes bounded and non-backtracking (fixed numeric character classes, no nested
quantifiers) — a migration file is untrusted input from a target project (threat T-04-03).
