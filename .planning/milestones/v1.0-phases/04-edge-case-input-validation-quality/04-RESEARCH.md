### Locked Decisions

**Permission/Role Edge Cases (DISC-05)**
- **D-01:** A second, optional test-user credential (`QA_AGENT_TOKEN_SECONDARY`) is introduced alongside Phase 1's `QA_AGENT_TOKEN`. When present, the agent actually executes "action outside the test user's role" cases using it. — Reversibility: costly (new env-var contract every installed project must know about).
- **D-02:** When `QA_AGENT_TOKEN_SECONDARY` is NOT configured for a project, permission/role cases are still generated into test-cases.md but marked `ejecución: pendiente — falta 2do usuario` — never silently dropped, never a hard failure of the whole run.
- **D-03:** Permission-boundary detection requires a net-new discovery surface: RLS policies (`CREATE POLICY ... WITH CHECK`, currently *deliberately excluded* by `scripts/discover-schema.mjs` per its own docblock) plus route-handler-level role/permission guards. This likely means extending `discover-schema.mjs` (or a sibling script) to parse `CREATE POLICY`, and orchestrator-judgment (Glob/Grep/Read, same pattern as Phase 3 D-08 route discovery) for in-code role checks. — Reversibility: costly (detection heuristic other permission-case generation depends on).
- **D-04:** Permission cases cover both API and UI execution layers (reuses the existing `ejecución: API | UI` field from Phase 3's D-03) — whichever layer the discovered check lives in determines how the case is later run.
- **D-05:** The agent does not require the user to describe the secondary user's role up front. It infers the role/permission delta by comparing what the primary vs. secondary credential can do, based on what it observes in code/responses — no new "role name" env var.

**Generation vs. Execution (stays aligned with Phase 3 D-10/D-11)**
- **D-06:** Edge/negative/permission cases generated by this phase are written to test-cases.md exactly like Phase 3's cases — generation remains a terminal step for the invocation. DISC-05's "genera y ejecuta" wording is satisfied by the existing Run protocol handoff (Phase 3 D-11), not by a new auto-execution path. This phase does NOT introduce auto-execution.
- **D-07:** After writing test-cases.md, the agent proactively offers to run the newly generated cases in the same response ("¿Corro estos N casos ahora?") — a UX convenience, not a behavior change: the user still must say yes, same confirmation-gated Run protocol as always.
- **D-08:** DISC-04 subcategories (required-field omission, invalid format, boundary value) get an explicit, human-readable subcategory noted in each case's title/steps (e.g., "campo requerido faltante: email", "límite superior: nombre > 50 caracteres") — no new field added to the existing 5-field schema (D-02 from Phase 3), just clearer titling so the user can scan test-cases.md without opening every case.

**Boundary-Value Exhaustiveness (DISC-04)**
- **D-09:** For a field with a discovered numeric/length constraint (SQL `CHECK`, or a Zod `.min()`/`.max()` the orchestrator read in a route/form file), the agent generates exactly 4 boundary cases: `min-1`, `min`, `max`, `max+1`.
- **D-10:** For a field with NO discovered constraint, the agent does not invent a boundary — same "shape observed, not invented" discipline as Phase 1 D-10 / Phase 3 D-12. If the field is required, it still gets a required-field-omission case; it just gets no min/max boundary cases.
- **D-11:** Invalid-format cases (email, date, regex-shaped fields) are limited to what the agent can detect in code (`z.string().email()`, `.regex(...)`, an SQL `CHECK` with a pattern, etc.). Domain-specific formats (CUIT/CUIL, Argentine phone numbers) are explicitly NOT added here — that's `DOM-01` in REQUIREMENTS.md's v2 section, intentionally out of this phase's scope.
- **D-12:** For numeric fields, boundary cases also include type-implied "odd" values (0, negative, decimal-in-integer-field) even without an explicit `CHECK`, when the column's data type/domain convention implies they should be rejected (e.g., an `INTEGER` "cantidad"/"precio" column). This is a type inference, not an invented arbitrary limit — distinguished from D-10's rule against inventing min/max thresholds.

**Scope of "Wrong Type / Out-of-Range" (DISC-05)**
- **D-13:** "Tipos incorrectos / fuera de rango" is strictly a data-contract violation: string where a number is expected, malformed JSON, an array where an object is expected, etc. It explicitly does NOT include injection-style payloads (SQL injection strings, `<script>` XSS payloads) — that's security testing, out of scope for this QA-functional agent (see `security-audit` skill for that concern instead).
- **D-14:** A wrong-type/out-of-range case's "resultado esperado" is a generic expectation ("debe rechazar la request"), not a hardcoded assumption of the exact HTTP status code. The actual observed code (400, 422, 500, or an unvalidated pass-through) is captured as evidence at run time — consistent with REP-01/SAFE-03's evidence-backed-verdict discipline, and avoids false "fail" verdicts on projects that don't follow REST status-code conventions to the letter.

## Summary

Phase 4 is a **pure extension** of Phase 1-3's already-built pipeline, not a new subsystem. Every mechanism it needs already has a direct precedent in this codebase: `discover-schema.mjs` is the deterministic-script tier for SQL parsing (already parses `CHECK`, already *excludes* `CREATE POLICY` by design — the exact gap D-03 asks to fill); `discovery-nextjs.md`'s imperative-validation regex is the existing required-field/format detection path (DISC-04 doesn't need a new detection mechanism, just systematic boundary generation layered on top); `references/destructive-classification.md`/`## Confirmation protocol` already gate every mutating call, so permission cases inherit the safety net for free; and `test-case-doc.mjs`/`references/test-case-format.md` is the existing document contract this phase's new case types must fit inside without breaking.

Two findings from this session are **load-bearing for planning** and are not obvious from CONTEXT.md alone:

1. **D-02's `ejecución: pendiente — falta 2do usuario` marker is not a valid value under the current schema.** `scripts/test-case-doc.mjs:48` hard-codes `export const EXECUTION_MODES = ['API', 'UI'];`, and both `parseCaseBlock` (throws `TestCaseFormatError`) and `validateTestCasesDoc` (pushes a validation error) reject any other literal in the `Ejecución` field. Since the Case generation protocol's own closing step requires `test-case-doc.mjs --file <path>` to exit 0 before the agent may report success, **a document containing an as-literally-decided `ejecución: pendiente — falta 2do usuario` case will fail this validation gate as the code stands today.** This is a concrete code change the plan must include — see Common Pitfalls and Open Questions below for the two resolution paths and my recommendation.
2. **Real route handlers in the target repos do not uniformly wrap permission failures in the `NextResponse.json({error:...}, {status:...})` shape** `discovery-nextjs.md`'s existing regex expects. `dotax` uses a custom `err(message, status)` helper in some handlers (`app/api/usuarios/route.ts:62`) alongside the inline shape elsewhere (`app/api/bejerman/sync/route.ts:24`). A role-guard Grep built only on the existing imperative-validation pattern will silently miss a real subset of permission checks. The plan needs a role-guard detection rule that Greps for the *comparison* (`.rol !== '<value>'`, `.rol === '<value>'`) independent of how the response is constructed, then Reads the surrounding lines to resolve the literal message/status by eye — mirroring `discovery-nextjs.md`'s own "read the handler body itself before concluding" guidance for the no-Zod case.

**Primary recommendation:** Extend `discover-schema.mjs` in place with two new exported functions — `extractPolicies()` (parses `CREATE POLICY` into structured records instead of only counting/skipping them) and `parseCheckBounds()` / `parseCheckEnum()` (extract numeric min/max or an allowed-value set from a raw `check` expression string already being returned) — keep `discover-schema.mjs` as the sole SQL-parsing tier per the project's established Deterministic-script vs. orchestrator-judgment split, and do role-guard/permission-case wiring as orchestrator-level Grep+Read exactly as Phase 3 did for route/form discovery.

### Pattern 1: Extend `discover-schema.mjs`'s `CREATE POLICY` branch from "count and skip" to "parse and return"

**What:** `extractConstraints()` (`scripts/discover-schema.mjs:472-508`) currently matches `/^CREATE\s+POLICY\b/i` and only counts `CHECK (` occurrences inside it (`withCheckSkipped`), explicitly never producing a record. A new `extractPolicies(sql, { file })` sibling function (mirroring `extractConstraints`'s own statement-splitting/line-citation machinery — `splitStatements`, `countNewlines`, `extractBalancedParens`) parses the real shape observed in every target repo this session:
```sql
CREATE POLICY usuarios_admin_write ON usuarios FOR ALL
  USING (rol_actual() = 'admin' AND tenant_id = tenant_actual())
  WITH CHECK (rol_actual() = 'admin' AND tenant_id = tenant_actual());
```
into `{ policyName, table, command, using, withCheck, source: { file, line } }`, where `command` is one of `SELECT|INSERT|UPDATE|DELETE|ALL` (default `ALL` when the `FOR` clause is absent — [CITED: postgresql.org/docs/current/sql-createpolicy.html]) and an optional `TO <role>` clause (not observed in any of the three target repos this session, but present in the Postgres grammar — parse it when present, `null` when absent).

**When to use:** Every `discoverSchema()` call — this becomes a new top-level `policies` array in the returned JSON, sibling to `enums` and `constraints`, always present (possibly empty).

**Grounded example** (`WITH CHECK` combined with `USING`, both required for an `ALL` policy in Postgres — the `WITH CHECK` falls back to `USING` for `UPDATE` when `WITH CHECK` is absent [CITED: postgresql.org/docs/current/sql-createpolicy.html]):
```sql
-- Source: c:/franquix/supabase/migrations/0001_init.sql:196-198 [VERIFIED, read this session]
CREATE POLICY usuarios_admin_write ON usuarios FOR ALL
  USING (rol_actual() = 'admin' AND tenant_id = tenant_actual())
  WITH CHECK (rol_actual() = 'admin' AND tenant_id = tenant_actual());
```
```sql
-- Source: c:/franquix/supabase/migrations/0001_init.sql:194-195 [VERIFIED, read this session]
-- A SELECT-only policy — no WITH CHECK at all, since SELECT never writes:
CREATE POLICY usuarios_self ON usuarios FOR SELECT
  USING (id = auth.uid() OR (rol_actual() = 'admin' AND tenant_id = tenant_actual()));
```

**Coverage variance across target repos — verify before assuming presence:** `dotax` has 72 `CREATE POLICY` occurrences across 33 migration files [VERIFIED: grep this session, `c:/dotax/supabase/migrations/*.sql`]; `franquix`'s `0001_init.sql` alone has 8+ policy blocks [CITED: 03-RESEARCH.md:322, cross-checked this session]. **`DATAX-web` has zero `CREATE POLICY` matches in its migrations directory** [VERIFIED: grep this session, `c:/DATAX-web/supabase/migrations`] — the new `policies` array must default to an empty array cleanly for a repo with no RLS, and the case-generation step must not treat an empty `policies` array as a discovery failure.

### Pattern 2: Extract numeric bounds from an already-captured `check` expression string

**What:** `extractConstraints()` already returns each constraint's raw SQL expression as a string in its `check` field (`scripts/discover-schema.mjs:261-266`, `328-347`). D-09 needs a new pure function, e.g. `parseCheckBounds(checkExpr)`, that recognizes the shapes actually observed this session and returns `{ min, max }` (either may be `null` when only one-sided) or `null` when the expression doesn't match a recognized numeric-bound shape (D-10's "don't invent a boundary" applies to the unmatched case too):

```js
// Grounded in real CHECK expressions read this session:
// c:/franquix/supabase/migrations/0005_franquicias_tipo_horario.sql:5
//   "dia_cierre BETWEEN 0 AND 6"                    -> { min: 0, max: 6 }
// c:/dotax/supabase/migrations/0011_minimos.sql:10
//   "minimo >= 0"                                   -> { min: 0, max: null }
// c:/franquix/supabase/migrations/0042_politica_entregas_oc.sql:47
//   "cantidad > 0"                                  -> { min: 1, max: null }  (exclusive -> min+1)
export function parseCheckBounds(checkExpr) {
  const between = checkExpr.match(/\bBETWEEN\s+(-?\d+(?:\.\d+)?)\s+AND\s+(-?\d+(?:\.\d+)?)\b/i);
  if (between) return { min: Number(between[1]), max: Number(between[2]) };
  const gte = checkExpr.match(/>=\s*(-?\d+(?:\.\d+)?)/);
  const lte = checkExpr.match(/<=\s*(-?\d+(?:\.\d+)?)/);
  const gt = checkExpr.match(/(?<!=)>\s*(-?\d+(?:\.\d+)?)/);
  const lt = checkExpr.match(/(?<!=)<\s*(-?\d+(?:\.\d+)?)/);
  const min = gte ? Number(gte[1]) : gt ? Number(gt[1]) + 1 : null;
  const max = lte ? Number(lte[1]) : lt ? Number(lt[1]) - 1 : null;
  return (min !== null || max !== null) ? { min, max } : null;
}
```
D-09's exact 4-case rule (`min-1, min, max, max+1`) only fires when **both** bounds resolve; a one-sided bound (e.g. `minimo >= 0`, no upper bound observed) still grounds a `min-1`/`min` pair without inventing a `max` — this is D-10's discipline applied inside the boundary generator itself, not just at the "no constraint at all" level.

**When to use:** Every numeric-typed constraint record `discover-schema.mjs` already returns with a non-null `check`.

### Pattern 3: Extract an inline enum-like `CHECK (col IN (...))` separately from `CREATE TYPE ... AS ENUM`

**What:** `discover-schema.mjs`'s existing `enumMap` cross-reference (`discover-schema.mjs:582-587`) only recognizes a column whose declared SQL **type** matches a `CREATE TYPE <name> AS ENUM (...)` declaration. A second, structurally different shape appears in real migrations and is **not** currently captured as an enum by anything in the script:
```sql
-- Source: c:/franquix/supabase/migrations/0010_cuadro_resultados.sql:10 [VERIFIED, read this session]
tipo text NOT NULL CHECK (tipo IN ('ingreso', 'egreso')),
```
A new `parseCheckEnum(checkExpr)` function, applied the same way as `parseCheckBounds`, recognizes `<col> IN ('a', 'b', ...)` and returns the literal value list — grounding an "invalid value not in the allowed set" edge case (D-11's "regex-shaped fields" scope extends naturally to this enumerated-set shape, which is a format constraint, not a numeric boundary).

### Pattern 4: Route-handler role-guard detection — Grep the comparison, not the response shape

**What:** `discovery-nextjs.md`'s existing imperative-validation regex (`NextResponse\.json\(\s*\{\s*error:\s*'([^']*)'\s*\}\s*,\s*\{\s*status:\s*(\d{3})\s*\}\s*\)`) is the right detector for *inline* 4xx responses, but real permission guards in the target repos take at least two shapes:
```ts
// Inline shape — discovery-nextjs.md's existing regex matches this directly.
// Source: c:/franquix/app/api/categorias/[id]/route.ts:14 [VERIFIED, read this session]
if (perfil.rol !== 'admin') return NextResponse.json({ error: 'Solo el administrador' }, { status: 403 })
```
```ts
// Helper-wrapped shape — the existing regex does NOT match this; only the
// role comparison itself is visible in the same textual form.
// Source: c:/dotax/app/api/bejerman/sync/route.ts:24 [VERIFIED, read this session]
if (!perfil || perfil.rol !== "admin") return NextResponse.json({ ok: false, error: "Sólo Admin" }, { status: 403 })
// Source: c:/dotax/app/api/usuarios/route.ts:62 [VERIFIED, read this session]
if (!caller) return err("No autorizado. Solo un administrador puede crear usuarios.", 403);
```
**Recommended detection rule for the plan:** Grep matched route handlers for the role-comparison operator directly (`\.rol\s*[!=]==\s*['"]\w+['"]`, plus a secondary Grep for a 401/403-adjacent literal like `no autorizado`/`solo.*admin`/`status:\s*40[13]` within a few lines), independent of whether the surrounding response call is `NextResponse.json(...)` or a project-local helper — then **Read the matched lines** to resolve the literal message and status by eye, exactly as `discovery-nextjs.md`'s own closing guidance already requires for the no-Zod-schema case ("read the handler body itself before concluding"). Never assume a fixed response-wrapper shape is the only one a target project uses.

### Pattern 5: `QA_AGENT_TOKEN_SECONDARY` dispatch without putting the token in the orchestrator's argv

**What:** `api-client.mjs`'s `readConfig()` (`scripts/api-client.mjs:86-129`) already resolves `QA_AGENT_TOKEN` purely from `process.env` inside the script's own process — never as a CLI argument — which is exactly what keeps the credential out of the orchestrator's tool-call transcript (Pitfall 4's credential-isolation discipline, and `## UI authentication and session reuse`'s explicit statement of the same principle for `QA_AGENT_UI_PASSWORD`). D-01's secondary token must follow the identical discipline: add a **boolean** CLI flag (e.g. `--secondary`) that tells `readConfig()` to read `process.env.QA_AGENT_TOKEN_SECONDARY` instead of `process.env.QA_AGENT_TOKEN` — never a flag that takes the token value itself as an argument.
```js
// Extends scripts/api-client.mjs:86 readConfig({ baseUrlArg, projectRoot, storageStatePath, useSecondary } = {})
const token = process.env[useSecondary ? 'QA_AGENT_TOKEN_SECONDARY' : 'QA_AGENT_TOKEN'];
```
The existing ConfigError message pattern (`scripts/api-client.mjs:121-125`) should get a `useSecondary`-aware variant naming `QA_AGENT_TOKEN_SECONDARY` specifically, so a missing secondary credential produces the same "fail loudly, never send an empty Authorization header" guarantee D-09 (Phase 1) already established — this is also the mechanism D-02's "still generate but never silently drop" resolves through: **generation time** (orchestrator judgment, checking whether the key name is present in `.env.local`/shell env without reading its value) decides whether to write `Ejecución: API`/`UI` or the pending marker; **dispatch time** (`api-client.mjs --secondary`) is the second, independent check that actually enforces it if the document is later run anyway.

### Anti-Patterns to Avoid
- **Eyeballing `CREATE POLICY` text with a plain grep instead of extending the parser.** This is the exact anti-pattern `discover-schema.mjs`'s own docblock and 03-RESEARCH.md Pattern 3/Pitfall 2 already named and solved for `CHECK` vs. `WITH CHECK` — repeating it for policy *command type* (`FOR SELECT` vs. `FOR ALL`) or the `TO <role>` clause would reintroduce the same class of bug this project has already paid down.
- **Assuming every permission check is a `NextResponse.json({error:...}, {status:...})` literal.** Confirmed false in `dotax` this session (Pattern 4) — a role-guard detector built only on the existing regex silently under-reports permission cases exactly the way Phase 3's Pitfall 1 (no-Zod assumption) already warned about for validation generally.
- **Passing `QA_AGENT_TOKEN_SECONDARY`'s value as a CLI argument.** Breaks the credential-isolation guarantee every other secret in this project already respects (`QA_AGENT_TOKEN`, `QA_AGENT_UI_PASSWORD`) — resolve it inside `readConfig()`/`process.env` only, never in an orchestrator-constructed argv string.
- **Inventing a numeric boundary when `parseCheckBounds`/`parseCheckEnum` return `null`.** D-10 is explicit and applies at the per-function level, not just "no CHECK found at all" — a `CHECK` that exists but doesn't match a recognized shape (e.g., a non-numeric business-rule expression like `num_nonnulls(objetivo_id, deposito_id) = 1` [VERIFIED: c:/dotax/supabase/migrations/0044_requerimientos_destino.sql:78]) still yields no boundary case, only (at most) a generic edge case citing the constraint's existence.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|--------------|-----|
| Parsing a Postgres `CREATE POLICY` statement | A general-purpose SQL grammar parser | Regex + balanced-paren extraction extending `discover-schema.mjs`'s existing `extractBalancedParens`/`splitStatements` machinery | Same reasoning `discover-schema.mjs`'s own header comment already gives for the rest of the file — the observed shape across all three repos is a fixed, small grammar subset (`CREATE POLICY <name> ON <table> [FOR <cmd>] [TO <role>] [USING (...)] [WITH CHECK (...)]`), and a full parser is disproportionate machinery for it |
| Extracting numeric bounds from a `CHECK` expression | A generic SQL expression evaluator/AST | Targeted regex for `BETWEEN`, `>=`/`<=`/`>`/`<` shapes only, returning `null` for anything else (D-10 discipline) | Every observed numeric CHECK in all three repos matches one of these four shapes; a full expression evaluator would need to handle arbitrary boolean logic this phase has no use for |
| Diffing what a primary vs. secondary credential can do (D-05) | A new role/permission taxonomy or classifier | Orchestrator judgment comparing two already-captured `api-client.mjs` JSON results (status code + response shape) for the same case | Phase 1/2 already produce structured, evidence-backed JSON per call — D-05 explicitly asks for inference from *observed* responses, not a modeled permission system |

**Key insight:** Every piece of "don't hand-roll" advice in this phase is the same principle 03-RESEARCH.md already established for Phase 3: the target repos' actual code shape is narrow and consistent enough that targeted regex + Read-to-confirm beats general-purpose parsing machinery every time — the only genuinely new *parsing* surface (as opposed to *judgment*) is `CREATE POLICY`, and it's a small, well-documented grammar subset [CITED: postgresql.org/docs/current/sql-createpolicy.html].

## Common Pitfalls

### Pitfall 1: D-02's `ejecución: pendiente` value is currently rejected by `test-case-doc.mjs`'s own schema
**What goes wrong:** The plan implements D-02's decision literally, the orchestrator writes a case with `Ejecución: pendiente — falta 2do usuario`, and the Case generation protocol's own mandatory closing step (`node <skill-dir>/scripts/test-case-doc.mjs --file <path>`) exits 9, because `EXECUTION_MODES = ['API', 'UI']` [VERIFIED: scripts/test-case-doc.mjs:48 — `export const EXECUTION_MODES = ['API', 'UI'];`] and both `parseCaseBlock` (`scripts/test-case-doc.mjs:140-145`, throws `TestCaseFormatError` for a value outside this set) and `validateTestCasesDoc` (`scripts/test-case-doc.mjs:505-514`, pushes an error for the same reason) reject any other literal.
**Why it happens:** D-02 was decided in isolation from the concrete validation code; CONTEXT.md's own D-04 note ("reuses the existing `ejecución: API | UI` field... whichever layer the discovered check lives in determines how the case is later run") assumes the field still carries real layer information even in a pending case, which is in tension with D-02's literal wording.
**How to avoid:** Resolve during planning, before implementation — see the two options and recommendation in Open Questions below. Whichever is chosen, the plan must update, together, in one task: `EXECUTION_MODES` (or an equivalent second field), `parseCaseBlock`'s per-field validation, `validateTestCasesDoc`'s `counts.byEjecucion` initialization and increment logic, `references/test-case-format.md`'s "Allowed values" section, and `## Running generated cases` step 4's dispatch branch (must explicitly refuse to dispatch a pending case with a clear message, never silently attempt it).
**Warning signs:** `test-case-doc.mjs --file <path>` exits 9 the first time a permission case with no secondary credential is generated during implementation testing; existing `test-case-doc.test.mjs` assertions about `EXECUTION_MODES`/`byEjecucion` fail after the change if the counts object isn't updated in lockstep.

### Pitfall 2: `withCheckSkipped`'s existing meaning breaks once `CREATE POLICY` is actually parsed
**What goes wrong:** `discover-schema.mjs`'s `withCheckSkipped` counter and its doc comment (`scripts/discover-schema.mjs:462-471`) currently mean "a `CHECK (` was seen inside a `CREATE POLICY` and deliberately excluded." Once Pattern 1 above makes the script actually parse and return policy records, every `WITH CHECK (...)` inside a policy is no longer "skipped" — it's captured. Existing tests in `discover-schema.test.mjs` that assert specific `withCheckSkipped` counts (following the pattern shown at lines 57-60 of that file) will need updating, and the field's own semantics need a decision: keep it counting `WITH CHECK` occurrences as a "captured, not skipped" informational count, rename it, or drop it now that the underlying gap is closed.
**Why it happens:** The counter's whole reason for existing (per its own doc comment) is to make "deliberately excluded" visible to a reader — extending the parser to no longer exclude that content removes the premise the counter's name and doc comment rest on.
**How to avoid:** Decide explicitly during planning whether `withCheckSkipped` is renamed/repurposed or removed, and update every existing test asserting on it in the same task that adds `extractPolicies()` — never let the field's old meaning and new behavior silently drift apart.
**Warning signs:** `discover-schema.test.mjs` tests fail after adding policy parsing, or (worse) pass with a now-misleading `withCheckSkipped` count still present in the JSON output that no downstream document reader can trust.

### Pitfall 3: Treating an empty discovered-`policies`/no-role-guard result as "no permission boundaries exist"
**What goes wrong:** `DATAX-web` has zero `CREATE POLICY` matches [VERIFIED this session]. A case-generation pass that reads an empty `policies` array as "this app has no permission edge cases" instead of "no RLS policies were found by this parser" would under-report exactly the way `discovery-nextjs.md`'s own "rule that follows from finding nothing" (lines 61-67 of that file) already warns against for validation detection generally — the same discipline must extend to permission detection, and DATAX-web's route handlers still need the in-code role-guard Grep (Pattern 4) run independently of RLS presence.
**Why it happens:** It's easy to conflate "the RLS-specific parser found nothing" with "there is no access control in this app" when the two detection paths (RLS and in-code guards) aren't clearly separated in the generated document's provenance.
**How to avoid:** Always run both detection paths (RLS via `discover-schema.mjs`, in-code guards via orchestrator Grep/Read) independently and report which one(s) actually contributed to each generated case — never treat one path's empty result as evidence about the other.
**Warning signs:** A generated test-cases.md for a project with real route-level role checks (like DATAX-web, per its dotax/franquix siblings' pattern) but zero permission cases, with no note explaining that RLS wasn't found rather than that permissions don't exist.

### Pitfall 4: Reading `QA_AGENT_TOKEN_SECONDARY`'s presence by printing or echoing it
**What goes wrong:** To decide whether to write `Ejecución: API/UI` or the pending marker (D-02) at generation time, the orchestrator needs to know whether `QA_AGENT_TOKEN_SECONDARY` is configured — but doing this by reading `.env.local`'s contents with the `Read` tool, or running a Bash command that echoes the variable's value, puts the secret in the conversation transcript, violating the exact discipline `## UI authentication and session reuse` already established for `QA_AGENT_UI_PASSWORD` ("never echoed into chat").
**Why it happens:** The simplest-looking way to check "is this configured" is to look at the file/variable directly, and the boundary between "checking presence" and "reading the value" is easy to blur in a single grep/cat command.
**How to avoid:** Check *presence only*, never the value — e.g. a Bash existence check like `grep -q '^QA_AGENT_TOKEN_SECONDARY=' <target>/.env.local` (exit code only, output discarded) or a shell test against `process.env` inside a script invocation whose only stdout is a boolean/JSON `{ "configured": true }`, mirroring how `readConfig()` itself already keeps the plaintext token inside its own process boundary.
**Warning signs:** A transcript or `results.json` file containing the literal secondary-token value anywhere outside `api-client.mjs`'s own in-process env read.

```
CREATE POLICY name ON table_name
    [ AS { PERMISSIVE | RESTRICTIVE } ]
    [ FOR { ALL | SELECT | INSERT | UPDATE | DELETE } ]
```

## Open Questions

1. **How should D-02's `ejecución: pendiente — falta 2do usuario` state coexist with D-04's requirement that `Ejecución` still records which layer (API/UI) a permission case belongs to?**
   - What we know: `EXECUTION_MODES` is currently a hard 2-value enum (`API`, `UI`) enforced by both `parseCaseBlock` and `validateTestCasesDoc`; D-02's literal wording implies the `Ejecución` field's *value* becomes the pending marker; D-04 implies the field should still resolve to a dispatchable layer.
   - What's unclear: Whether the user intends the pending state to *replace* the API/UI value (losing which layer it is until the document is hand-edited or regenerated — acceptable per D-06's "meant to be edited by hand" discipline) or to *coexist* with it (requiring a schema change beyond a single field's allowed-value set).
   - Recommendation: **Extend `EXECUTION_MODES` to `['API', 'UI', 'pendiente']`** (or a similarly named third literal) as the lower-diff option, and treat the loss of layer granularity as acceptable given D-06 already establishes the document is hand-edited before any case is run — a user who later configures `QA_AGENT_TOKEN_SECONDARY` edits the `Ejecución` field back to `API`/`UI` themselves, or the agent regenerates. This must update, together: `test-case-doc.mjs`'s `EXECUTION_MODES` array, `parseCaseBlock`/`validateTestCasesDoc`'s per-field checks, `counts.byEjecucion`'s three-key shape, `references/test-case-format.md`'s "Allowed values" section, and `## Running generated cases` step 4's dispatch logic (new branch: report "cannot run — pendiente, falta QA_AGENT_TOKEN_SECONDARY" and stop for that case, never attempt dispatch). Flag this resolution to the user/plan-checker before implementation, since it is a genuine schema-contract fork CONTEXT.md's own two decisions (D-02, D-04) didn't fully reconcile.

2. **Should the new `--secondary` CLI flag on `api-client.mjs` be a boolean switch or should `readConfig` accept an explicit `tokenEnvVar` parameter for future extensibility?**
   - What we know: D-01 only requires exactly one additional credential (`QA_AGENT_TOKEN_SECONDARY`) — no third+ tier of permission testing is in scope.
   - What's unclear: Whether a future phase (not in this milestone) might want a third role. Nothing in REQUIREMENTS.md v2 suggests this.
   - Recommendation: Keep it a simple boolean flag (`--secondary`) matching the minimal, YAGNI-consistent style the rest of this codebase uses (e.g. `--read-only-intent`, `--allow-non-local` are all booleans, not parameterized). Revisit only if a future milestone genuinely adds a third credential tier.
