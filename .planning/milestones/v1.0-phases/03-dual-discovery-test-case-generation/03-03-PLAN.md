<objective>
**As a** developer who already has a generated list of test cases, **I want to** ask for a specific flow to be documented on its own, and later say "run cases 1, 3 and 5" and have them actually run, **so that** the document the agent wrote is something I use rather than something I read once.

This plan closes the phase's two remaining halves. The first is DISC-03: a one-off instruction produces the same kind of document a full scan does, grounded in the specific files the named flow lives in and nothing else. The second is the handoff D-11 describes — the document stops being an artifact and becomes an input to the executors Phase 1 and Phase 2 already built, without introducing a second execution path.

Purpose: two of this phase's decisions only pay off here. D-06 made the document editable by hand, which means the agent must re-read it at execution time rather than trusting what it wrote — a document the developer struck cases out of is the point, not an inconvenience. And D-04's short IDs are only usable if looking one up is reliable; RESEARCH Pitfall 5 shows a bare `case-1` is a substring of `case-12`, so the lookup has to be anchored rather than grepped and read by eye. That is the same discipline this project already applies to HTTP verdicts, applied to document lookup.

Output: anchored lookup and full validation on `scripts/test-case-doc.mjs` with its CLI, a scoped golden document, and the two `SKILL.md` additions that make a one-off instruction and a run-by-ID request both work.

Implements D-04 (document-scoped sequential IDs, now with a collision-proof lookup), D-06 (the document is editable and re-read at execution time), D-10 (generation is terminal), D-11 (running cases hands to the existing Phase 1/2 protocols unchanged) and D-12 (a scoped instruction reads the files the flow names and fabricates nothing).
</objective>
