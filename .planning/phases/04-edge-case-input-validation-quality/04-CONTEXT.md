# Phase 4: Edge-Case & Input Validation Quality - Context

**Gathered:** 2026-09-17
**Status:** Ready for planning

<domain>
## Phase Boundary

Building on top of Phase 3's discovery (`discover-schema.mjs` constraints, Zod schemas the orchestrator reads at route/form level), the agent makes its test-case generation systematically cover input-validation boundaries (DISC-04: required-field omission, invalid formats, boundary values) and negative/permission edge scenarios (DISC-05: out-of-range data, wrong data types, permission/auth edge cases) — not just the happy path Phase 3 already produces. This phase extends test-case *generation* (still terminal per Phase 3's D-10 — no auto-execution) with a second, systematic pass over discovered fields/constraints, plus a net-new detection surface for permission/role boundaries that didn't exist before this phase. It does not touch API/UI execution engines (Phase 1/2, unchanged) or introduce security/injection testing (out of scope — belongs to a security tool, not this QA agent).

</domain>

<decisions>
## Implementation Decisions

### Permission/Role Edge Cases (DISC-05)
- **D-01:** A second, optional test-user credential (`QA_AGENT_TOKEN_SECONDARY`) is introduced alongside Phase 1's `QA_AGENT_TOKEN`. When present, the agent actually executes "action outside the test user's role" cases using it. — **Reversibility:** costly — becomes a new env-var contract every installed project must know about; changing the name/shape later means updating every project's `.env.local` and this skill's docs.
- **D-02:** When `QA_AGENT_TOKEN_SECONDARY` is NOT configured for a project, permission/role cases are still generated into test-cases.md but marked `ejecución: pendiente — falta 2do usuario` — never silently dropped, never a hard failure of the whole run. Keeps DATAX/dotax/franquix working unchanged until/unless the user opts in.
- **D-03:** Permission-boundary detection requires a net-new discovery surface: RLS policies (`CREATE POLICY ... WITH CHECK`, currently *deliberately excluded* by `scripts/discover-schema.mjs` per its own docblock — policy predicates vs. data constraints share the same `CHECK (...)` syntax) plus route-handler-level role/permission guards. This likely means extending `discover-schema.mjs` (or a sibling script) to parse `CREATE POLICY`, and orchestrator-judgment (Glob/Grep/Read, same pattern as Phase 3 D-08 route discovery) for in-code role checks. — **Reversibility:** costly — the detection heuristic other permission-case generation depends on.
- **D-04:** Permission cases cover both API and UI execution layers (reuses the existing `ejecución: API | UI` field from Phase 3's D-03) — whichever layer the discovered check lives in determines how the case is later run.
- **D-05:** The agent does not require the user to describe the secondary user's role up front. It infers the role/permission delta by comparing what the primary vs. secondary credential can do, based on what it observes in code/responses — no new "role name" env var.

### Generation vs. Execution (stays aligned with Phase 3 D-10/D-11)
- **D-06:** Edge/negative/permission cases generated by this phase are written to test-cases.md exactly like Phase 3's cases — generation remains a terminal step for the invocation. DISC-05's "genera y ejecuta" wording is satisfied by the existing Run protocol handoff (Phase 3 D-11), not by a new auto-execution path. This phase does NOT introduce auto-execution.
- **D-07:** After writing test-cases.md, the agent proactively offers to run the newly generated cases in the same response ("¿Corro estos N casos ahora?") — a UX convenience, not a behavior change: the user still must say yes, same confirmation-gated Run protocol as always.
- **D-08:** DISC-04 subcategories (required-field omission, invalid format, boundary value) get an explicit, human-readable subcategory noted in each case's title/steps (e.g., "campo requerido faltante: email", "límite superior: nombre > 50 caracteres") — no new field added to the existing 5-field schema (D-02 from Phase 3), just clearer titling so the user can scan test-cases.md without opening every case.

### Boundary-Value Exhaustiveness (DISC-04)
- **D-09:** For a field with a discovered numeric/length constraint (SQL `CHECK`, or a Zod `.min()`/`.max()` the orchestrator read in a route/form file), the agent generates exactly 4 boundary cases: `min-1`, `min`, `max`, `max+1`.
- **D-10:** For a field with NO discovered constraint, the agent does not invent a boundary — same "shape observed, not invented" discipline as Phase 1 D-10 / Phase 3 D-12. If the field is required, it still gets a required-field-omission case; it just gets no min/max boundary cases.
- **D-11:** Invalid-format cases (email, date, regex-shaped fields) are limited to what the agent can detect in code (`z.string().email()`, `.regex(...)`, an SQL `CHECK` with a pattern, etc.). Domain-specific formats (CUIT/CUIL, Argentine phone numbers) are explicitly NOT added here — that's `DOM-01` in REQUIREMENTS.md's v2 section, intentionally out of this phase's scope.
- **D-12:** For numeric fields, boundary cases also include type-implied "odd" values (0, negative, decimal-in-integer-field) even without an explicit `CHECK`, when the column's data type/domain convention implies they should be rejected (e.g., an `INTEGER` "cantidad"/"precio" column). This is a type inference, not an invented arbitrary limit — distinguished from D-10's rule against inventing min/max thresholds.

### Scope of "Wrong Type / Out-of-Range" (DISC-05)
- **D-13:** "Tipos incorrectos / fuera de rango" is strictly a data-contract violation: string where a number is expected, malformed JSON, an array where an object is expected, etc. It explicitly does NOT include injection-style payloads (SQL injection strings, `<script>` XSS payloads) — that's security testing, out of scope for this QA-functional agent (see `security-audit` skill for that concern instead).
- **D-14:** A wrong-type/out-of-range case's "resultado esperado" is a generic expectation ("debe rechazar la request"), not a hardcoded assumption of the exact HTTP status code. The actual observed code (400, 422, 500, or an unvalidated pass-through) is captured as evidence at run time — consistent with REP-01/SAFE-03's evidence-backed-verdict discipline, and avoids false "fail" verdicts on projects that don't follow REST status-code conventions to the letter.

### Claude's Discretion
- Exact Markdown phrasing/formatting of the new boundary-case titles (D-08) — constrained by "human-readable subcategory," not a fixed template.
- Whether the `CREATE POLICY` parser (D-03) lives inside `discover-schema.mjs` or as a new sibling script — an implementation/architecture call for planning, not discussed here.

</decisions>

## Existing Code Insights

### Reusable Assets
- `scripts/discover-schema.mjs`: `extractConstraints()` already parses `NOT NULL`/`UNIQUE`/`PRIMARY KEY`/`REFERENCES`/`CHECK`/`DEFAULT` and enum types from SQL migrations — the source of truth for D-09's numeric/length boundaries on DB-backed fields. Its `CREATE POLICY` exclusion is exactly the gap D-03 needs to fill.
- `scripts/test-case-doc.mjs`: existing case-writing logic from Phase 3 — this phase extends its inputs (new case subtypes, new `ejecución: pendiente` state for D-02) rather than replacing it.
- `scripts/api-client.mjs`, `scripts/ui-login.mjs`, `scripts/ui-case.mjs`: existing auth/execution paths D-01's secondary credential and D-04's UI-layer permission cases plug into unchanged.
- `references/destructive-classification.md`, `references/ui-destructive-classification.md`: unchanged — a permission/edge case executed later still passes through these existing gates (D-06 doesn't touch this).

### Established Patterns
- Deterministic-script vs. orchestrator-judgment split (Phase 1, reused every phase since): `discover-schema.mjs` stays the deterministic SQL-parsing tier; route/form/role-check discovery in TypeScript source stays orchestrator judgment (Glob/Grep/Read) — D-03 follows this same split for RLS (script) vs. code-level guards (orchestrator).
- `qa-reports/<run-id>-test-cases.md` naming and per-surface grouping (Phase 3 D-01/D-05) — unchanged; this phase's new case types slot into the same document and grouping.

### Integration Points
- `.env.local` / `readConfig()` env-var loading (Phase 1) — D-01 adds `QA_AGENT_TOKEN_SECONDARY` to this existing loading path, optional/absent-safe per D-02.
- `qa-reports/` output directory — no new output location; boundary/permission cases land in the same `test-cases.md` Phase 3 already produces.
