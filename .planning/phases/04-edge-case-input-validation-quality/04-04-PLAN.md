<objective>
Make the case-document contract able to carry D-02's state — a permission case that was
generated but cannot be run because no secondary test credential is configured — without
breaking the validation gate that `## Case generation protocol` requires before the agent
may report success, and without silently discarding D-04's record of which execution layer
the case belongs to.

Purpose: D-02 and D-04 were decided separately and do not fully reconcile. `EXECUTION_MODES`
is a hard two-value enum enforced in three places today, so a document written exactly as
D-02 words it exits 9 at the protocol's own closing validation step. That fork is resolved
at this plan's decision checkpoint before any code is written, because it is a contract
change with downstream consumers in `references/test-case-format.md` and in every dispatch
path.

Output: the pending execution state implemented across `scripts/test-case-doc.mjs`,
documented in `references/test-case-format.md`, and locked by tests.
</objective>

<task type="checkpoint:decision" gate="blocking">
  <name>Task 1: Decide how `Ejecución` records a generated-but-not-runnable permission case</name>
  <decision>How the case document represents a permission case generated while `QA_AGENT_TOKEN_SECONDARY` is absent — D-02 says the case is marked `pendiente — falta 2do usuario`, D-04 says the same field still records whether the case is an API or a UI case.</decision>
  <context>
`scripts/test-case-doc.mjs` hard-codes `EXECUTION_MODES` as exactly `['API', 'UI']` and enforces
it in `parseCaseBlock` (throws `TestCaseFormatError`), in `validateTestCasesDoc` (collects an
error), and in `counts.byEjecucion` (a two-key object). `## Case generation protocol` requires
`node scripts/test-case-doc.mjs --file <path>` to exit 0 before the agent may tell the developer
a document is ready — so a document written exactly as D-02 words it fails that gate today.

This is a contract change, not an implementation detail: `references/test-case-format.md`
publishes the allowed values, and `## Running generated cases` step 4 dispatches on them. Undoing
it later means changing the format contract, the reader, and both dispatch branches together.
04-RESEARCH.md raised this as Open Question 1 and flagged its own recommendation as an
assumption to confirm before implementation rather than a locked decision.

Both D-02 and D-04 are locked user decisions. Neither is being dropped here — you are choosing
which representation carries both.
  </context>
  <options>
    <option id="option-a">
      <name>Third literal: `Ejecución` becomes one of API, UI, pendiente</name>
      <pros>Smallest diff — one array literal, the two existing enum checks, one counts key, one doc section. This is 04-RESEARCH.md's own recommendation. The document is meant to be hand-edited before any case runs (D-06), so a developer who later configures the secondary credential edits the field back to API or UI, or regenerates.</pros>
      <cons>The pending case stops recording which layer it belongs to, so D-04's "whichever layer the discovered check lives in determines how the case is later run" is not readable from the document until it is hand-edited or regenerated. The reason for the pending state ("falta 2do usuario") has nowhere structured to live.</cons>
    </option>
    <option id="option-b">
      <name>Qualified value: `Ejecución` stays API or UI and carries a pending qualifier</name>
      <pros>Satisfies both locked decisions at once — the layer is still recorded (D-04) and the case is still visibly marked pending with its reason (D-02). The reason string is parsed rather than lost, so `## Running generated cases` can refuse dispatch with the document's own explanation. A case becomes runnable by deleting the qualifier, a smaller hand-edit than rewriting the value.</pros>
      <cons>Larger parser diff — `parseCaseBlock`, `findCase` and `validateTestCasesDoc` must all split the qualifier from the layer before the enum check, and the parsed-case shape grows two fields. The bullet line is longer and slightly less scannable than a bare literal.</cons>
    </option>
    <option id="option-c">
      <name>Sixth bullet: add a separate pending field to the case schema</name>
      <pros>Keeps `Ejecución` completely untouched; the pending state and its reason are unambiguously their own field.</pros>
      <cons>Breaks the five-field case schema Phase 3 locked as D-02 of that phase and which `CASE_FIELDS`, `references/test-case-format.md` and every existing generated document all assume. Every prior document becomes non-conforming or the field becomes optional, which reintroduces the silent-skip failure mode this module's doc comment says it exists to avoid.</cons>
    </option>
  </options>
  <resume-signal>Select: option-a, option-b, or option-c. The planner's recommendation is option-b, because it is the only one that keeps both D-02 and D-04 intact; 04-RESEARCH.md recommended option-a on lowest-diff grounds. Record the selection and the reasoning in `04-04-SUMMARY.md` before starting Task 2.</resume-signal>
</task>

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
