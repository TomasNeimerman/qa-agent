<objective>
**As a** developer installing the QA agent in one of our projects, **I want to** register the browser-control server once, with flags someone actually verified, **so that** the agent's first browser run works instead of failing on a guessed command-line flag.

Purpose: RESEARCH could not verify two things hands-on and said so plainly. Assumption A2 — that Playwright MCP's default persistent profile is a Chromium user-data directory rather than a reusable `storageState` JSON, and that the isolated mode plus a storage capability is what produces a consumable file — was synthesised from summarised documentation. Assumption A4 — the exact spelling of the capability flag — has the same provenance. RESEARCH's own recommendation was that a plan verify these hands-on before anything is built on them. This plan is that verification, isolated into its own small unit so a surprise costs a correction to one JSON file and one document rather than a rewrite of the run protocol.

It also carries this phase's mandated package-legitimacy gate. The audit returned a suspicious verdict for `@playwright/mcp` on a publish-recency heuristic, and protocol is explicit that such a verdict is confirmed by a human before the package runs, never rubber-stamped past.

Output: a registered, exercised Playwright MCP server and a written setup procedure that records what was actually observed, including any correction to the research assumptions.

Implements D-01 (Playwright MCP as the browser-control mechanism) and D-02 (a single Chromium context, no cross-browser matrix).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| npm registry → this machine | `npx @playwright/mcp@latest` fetches and executes third-party code with the developer's own privileges |
| MCP server process → target app | The server drives a real browser against a real localhost or staging environment |
| storage-state file → MCP server startup | A live session credential is handed to a separate process at launch |
| target app page content → orchestrator context | Page text read back through `browser_snapshot` enters the model's context and is acted on |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-SC | Tampering | `npx @playwright/mcp@latest` supply chain | high | mitigate | Blocking human checkpoint before first execution, confirming the exact scoped package name, the Microsoft source repository and a download volume inconsistent with a slopsquat — the audit's SUS verdict is resolved by a person, never auto-approved |
| T-02-15 | Spoofing | a near-miss package name resolving instead of the intended one | high | mitigate | The checkpoint enumerates the specific near-miss spellings to reject by name, and `.mcp.json` pins the full scoped specifier `@playwright/mcp@latest` rather than a bare name |
| T-02-16 | Information Disclosure | a session leaking between unrelated target projects through a shared browser profile | medium | mitigate | The server is registered in isolated-profile mode so no cross-run user-data directory is kept; each run's session comes from that run's own storage-state file |
| T-02-17 | Tampering | prompt injection through page content reflected into snapshot output | medium | accept | Inherent to any agent that reads live page content. Bounded rather than eliminated: no JavaScript-evaluation capability is enabled in the registration, so the agent cannot be talked into executing arbitrary script in the page, and the destructive-action gate from plan 02-02 still stands between any suggested action and a real mutation |
| T-02-18 | Denial of Service | an unpinned `@latest` specifier changing behaviour mid-project | low | accept | Accepted for now, consistent with RESEARCH's own note that this is a fast-moving sub-1.0 package where pinning would strand the project on a stale protocol. `references/mcp-setup.md` records the exact version verified, so a later behaviour change is diagnosable |
</threat_model>
